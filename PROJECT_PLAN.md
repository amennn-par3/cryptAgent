# Cryptagent — revised midterm and end-term plan

This plan supersedes the previous Phase 1–3 design. The project is restarting from
this scope. The old files are still present because the execution environment blocked
recursive deletion even after a write-permission request was granted. They are legacy
materials, not completed work for this revised plan.

## Goal

First build a small, working verifier with fixed choices for the midterm. Then extend
the same backend into an LLM-powered generator/verifier with selectable profiles for
the end term. Keep the implementation simple and demonstrate actual checks.

## Midterm: the code is the only variable input

| Item | Fixed choice |
|---|---|
| Language | C++20 |
| Environment | Native Windows x64 with Visual Studio 2022/MSVC |
| Cryptographic library | libsodium |
| Scheme | XChaCha20-Poly1305 authenticated encryption |
| Code scope | Small in-memory encryption/decryption functions or modules |
| Attacker | Can modify ciphertext, authentication tag, nonce and associated data, and observe returned status/output |
| Assumptions | Trusted OS, library and cryptographic randomness; secret key unavailable to attacker |
| User input | C++ source, including supporting headers/build context when necessary |
| Output | Findings, evidence, limitations and verdict |
| No midterm features | Generation, automatic repair, scheme/attacker selection, timing/power analysis or protocol proofs |

Keys and messages used by tests are synthetic data generated by the backend. The
user does not select these as additional midterm settings. Replay prevention is out
of scope; previously valid messages can be decrypted again.

### What 'any piece of code' means

Allow code to be pasted or uploaded. Check whether it matches the supported scheme,
language and small-module scope, and whether enough context is available to test it.
A missing entry point, unrelated algorithm or unsupported application receives an
inconclusive result with an explanation. Start with one documented test interface.
Do not silently rewrite submitted code or claim universal verification of arbitrary C++.

### Fixed midterm checklist

1. Supported code compiles and encrypts/decrypts valid synthetic messages correctly.
2. Tampered ciphertext/tag, a wrong key and changed associated data fail authentication.
3. Failed authentication returns an error without exposing plaintext.
4. Key/nonce APIs are used correctly, including fresh production nonce generation
   rather than a hardcoded nonce.
5. Malformed lengths and selected boundary inputs are rejected safely.

Use targeted source checks and native tests. Nonce sampling alone does not prove
uniqueness or randomness. Tests do not prove every execution safe. Report source
suspicions separately from confirmed violations. Timing, register erasure and general
memory-safety proof are not midterm claims.

### User flow

Submit source -> validate supported scope -> inspect source and run tests -> collect
evidence -> show issues and verdict.

- **Fails selected checks:** at least one confirmed required violation.
- **Passes selected checks:** all required checks completed successfully for the fixed profile.
- **Inconclusive:** unsupported input, missing context, failed infrastructure or insufficient
  evidence, without a confirmed violation taking precedence.

Passing does not mean universally secure or automatically deployable.

## Work until midterm

| Step | Work | Deliverable |
|---|---|---|
| M1 — Setup | Install/pin the Windows tools and libsodium; define a small C++ interface | One reference example that actually compiles and runs |
| M2 — Verifier | Implement the five checks, collect evidence and derive verdicts | Working fixed-profile verifier |
| M3 — Demo | Add a simple paste/upload interface and about 10–15 examples | Midterm demonstration and short results report |

Build a command-line backend first, then the small presentation interface. Rules and
tests are sufficient for the midterm; no model training is needed. Before executing
arbitrary submissions, use an isolated Windows worker without credentials/network
access and with runtime limits. Until then, run only inspected project fixtures.

### Midterm demo example

Submit a decryption function that ignores authentication failure. The backend creates
synthetic inputs, encrypts a message, changes the tag and calls that function. If it
reports success or returns output after authentication fails, show the witness and
relevant code. Then submit a separately corrected function and repeat the checks.
This demonstrates verification; the system does not generate the correction.

## End term: selectable profiles and LLM generation

Retain C++20 and Windows. Introduce only a small supported set initially:

| Selection | Planned choices |
|---|---|
| Mode | Verify existing code; generate and verify code |
| Scheme | XChaCha20-Poly1305; one additional integration such as ChaCha20-Poly1305 IETF through libsodium |
| Attacker profile | Message tampering; message tampering plus observation of application logs |

The second attacker profile adds checks for secret disclosure through logs. It does
not grant arbitrary process-memory access. Each scheme has its own parameters and
test adapter; each attacker profile has explicit capabilities and evidence checks.
Support only combinations for which those checks exist. More schemes/profiles are
extensions, not prerequisites for the first final demonstration.

### Verify flow

Choose scheme + attacker profile + submit C++ -> load matching requirements -> run
checks -> LLM explains evidence -> deterministic policy produces the verdict.

### Generate flow

Choose scheme + attacker profile + describe the required function -> LLM generates
candidate C++ -> the same verifier checks it -> return code, findings and limitations.
Use an existing model. Fine-tuning and training from scratch are not required.
A small bounded revision loop is optional if time permits; it cannot weaken checks.

## Work after midterm

| Step | Work | Deliverable |
|---|---|---|
| E1 — Profiles | Move fixed choices into configuration; add one scheme and attacker profile | Selectable verifier |
| E2 — LLM | Connect generation and evidence-based explanations | Generate-and-verify workflow |
| E3 — Evaluation | Compare LLM-only output with the verified workflow on separate examples | Final demo, results and limitations |

Measure false acceptance of defective code, detected defects, inconclusive results,
functional correctness of generated code and assessment time. Keep development and
evaluation examples separate. Do not build another large synthetic corpus at the start.

## Immediate next step

Start M1 with one clean Windows/libsodium example. Resolve the missing sodium.h
dependency and obtain an actual successful compile/encrypt/decrypt run before adding
agent behavior or extra documentation. No new implementation is claimed in this plan.
