# Midterm dataset expansion

Verification remains the only application mode. This package adds authored examples
and executable fixture probes; it does not execute uploaded code in the web server.
The existing web UI is still the AES-only snapshot. Multi-profile UI activation and
replacement of its original provider client must follow the local model integration.

## Small initial scope

| Profile | Language/library | Targeted examples |
|---|---|---|
| AES-128-GCM | C++20 / Windows CNG | Existing F01–F05 source-review pilot |
| CKKS | Python / TenSEAL 0.3.16 | Secret-key export, result tampering, input-count limits |
| TFHE | Rust / TFHE-rs 1.4.3 | Secret-key export, result tampering, integer wraparound |
| BFV, lattice-based | C++20 / OpenFHE 1.4.2 | Secret-key export, result tampering, plaintext-domain overflow |

BFV supplies the requested C++ lattice-based example. A separate KEM profile is not
needed for this first expansion. CKKS/BFV examples perform shallow homomorphic
computations; this package does not demonstrate bootstrapping or arbitrary depth.

FHE ciphertext malleability is intentional. A defect here is releasing secrets,
violating an explicit numeric/input contract, or accepting a wrong result when the
toy client has an independently known answer. The corrected result examples use a
local reference check; they are not general verifiable-computation protocols.
H01–H05 are FHE-specific requirements, separate from AES F01–F05. Every record carries
its actual profile. Missing setup/lifecycle code stays insufficient_context.

## Dataset and evidence

`cases/` contains 18 source excerpts in nine defective/corrected pairs. Harnesses are
separate and are not included in model inputs. No labels are generated by the model.
`data/` combines those examples with the preserved initial AES pilot: 42 training,
6 validation, and 10 held-out records. Pair members always share a split; whitespace
variants in the initial AES set are not independent implementations. This is a small
plumbing/training pilot, not an independent-author benchmark or adequate evidence of
general security-review accuracy. The old 156 Python examples in `/home/hp/crypto-llm`
remain unchanged and are excluded because they do not match these review contracts.

Run from the repository root:

```bash
python3 training/expanded/build_dataset.py
python3 training/expanded/validate_dataset.py
python3 training/expanded/run_probes.py --out /absolute/path/to/new-native-run
```

Observed on this host: native run 02 compiled and executed all 18 FHE fixtures;
all nine defective/corrected pairs matched their authored targeted expectations.
Run 01 retained an initial C++ harness compile error and is superseded by run 02.
No whole-program correctness or model-accuracy claim follows from these results.

The probe runner rebuilds only these inspected fixtures, runs them on synthetic
inputs, and saves command arguments, stdout/stderr, exit codes, versions, source and
harness hashes, and expected-versus-observed comparisons. A failed build, timeout or
unavailable dependency is never counted as a passed check. Output directories must
be new, preserving earlier evidence.

## Installed local dependencies

To reproduce the project-local CPU setup on Ubuntu x86-64, run
`bash training/expanded/setup_cpu.sh` (requires network, Python venv support,
Git, wget, and a C++ compiler). It installs only under `runtime/`.

All added dependencies are under ignored `runtime/`; no system installation or
changes to the existing training virtual environment are needed:

- `runtime/fhe-venv/`: Python 3.10 with the pinned probe requirements.
- `runtime/openfhe/`: OpenFHE 1.4.2, source commit `aa391988d354d4360f390f223a90e0d1b98839d7`.
- `runtime/rust/`: Rust 1.91.1, downloaded from the official distribution and SHA-256 checked.
- `runtime/cargo/`: Rust dependencies; `rust/Cargo.lock` pins their versions/checksums.
- `runtime/node-v22.23.3-linux-x64/`: checksum-checked Node 22.23.3.

The CPU fixture environment deliberately uses TenSEAL 0.3.16 to match Python 3.10;
the latest release is not required for this pilot. Library versions are part of the
experimental profile, not a claim that these are recommended production releases.

## Training and model comparison

Use the already installed training environment and cached Llama weights:

```bash
/home/hp/crypto-llm/.venv/bin/python training/train.py --smoke --output training/runs/multi-smoke-v1
/home/hp/crypto-llm/.venv/bin/python training/train.py --epochs 2 --output training/runs/multi-pilot-v1
/home/hp/crypto-llm/.venv/bin/python training/expanded/compare_models.py --adapter training/runs/multi-pilot-v1/adapter --out /absolute/path/to/new-model-run
```

Run the full pilot only after the smoke test succeeds. Training is assistant-token-only
QLoRA (NF4, rank 16), entirely offline. The script refuses truncation and existing run
directories. Models/checkpoints/adapters are ignored by Git. The comparison records
raw base/fine-tuned outputs on the same frozen held-out set with deterministic
decoding, schema/quotation validation and timing. A CUDA preflight failure is stored
as not_run for both models; it is not an inference result.
