Cryptagent — Architecture and Evaluation Analysis

Windows C++ cryptographic code review · Recorded ten-case evaluation
Report basis: report schema 2.0; profile aes128-gcm-tampering-v1, version 1.0.0.
Run date: 16 September 2026, Asia/Kolkata (the raw records use UTC on 15 September).
Evidence: saved input files, individual response JSON, aggregate results, evaluation runner, and current application source. No new model calls were made for this report.

1. Agent structure and purpose

Cryptagent is currently a fixed-profile, LLM-assisted source reviewer. A local Windows web application accepts C++ source, performs a small set of textual checks, requests a structured review from GPT-6 Astra with medium reasoning, validates that response, and derives an overall assessment. It is not yet an executing or formally proving cryptographic verifier. Generation and learning are disabled.

The target is the integration of AES-128-GCM through Windows Cryptography Next Generation (CNG), not a new implementation of AES. GCM authenticates ciphertext and associated data as well as supporting encryption; nonce uniqueness belongs to its security requirements. These properties motivate the selected checks. NIST GCM specification.

The fixed profile specifies a 16-byte key, 12-byte nonce and 16-byte authentication tag. The attacker can modify encrypted inputs and observe public status/output but is assumed unable to read the key. Windows and CNG are trusted. Replay prevention, timing/physical side channels and universal memory-safety proofs are excluded. Consequently, the project's earlier idea of proving register erasure or resistance to physical leakage is not tested by this build.

1.3 Prompt and model contract

Every review uses the configured gpt-6-astra model and medium reasoning, with no fallback. The request carries three parts: trusted reviewer instructions, trusted profile/check descriptions, and the submitted source as untrusted numbered lines. Comments and strings must not be treated as instructions.

The requested JSON contains one scope classification, exactly five check assessments and up to eight findings. Per-check assessments are potential issue, no issue identified, insufficient context or not applicable. Findings require a check ID, a verbatim quotation, an exact line range of at most eight lines and a rationale. The backend rejects duplicates, inconsistent combinations, unsupported IDs and invalid references. An issue lacking an accepted reference is downgraded to insufficient context.

These controls constrain output format and provenance. They do not prove that a quoted passage actually has the claimed defect. The positive assessments are not independently proved and do not themselves require a quoted source excerpt; this is an important asymmetry for future evaluation.

1.4 Operational boundaries

The app binds to 127.0.0.1:8000, checks host/origin and a per-server session token, sets a content-security policy, and rejects unsupported request fields. Source is limited to 64 KiB and 2,000 lines. It allows up to two active requests, including connection operations. The model request uses a 120-second timeout, a bounded response size, an 8,000-output-token cap, disabled truncation and store:false.

The API key entered through the page is held in server memory; the input clears after submission. Submitted code is sent to OpenAI when review is attempted. store:false is a request setting, not a blanket guarantee of zero provider retention. The normal verifier does not persist submitted source; the evaluation runner deliberately saves these test inputs and response records. Thus sourceStored:false in an agent response describes the verifier, not the entire evaluation workflow.

“Access confirmed” comes from retrieving the model's metadata successfully. It does not test a successful Responses API review or guarantee available quota. The cached access result can therefore coexist with failed reviews.

3. Evaluation design and data integrity

The intended suite comprises six single-mutation issue fixtures, one intended positive baseline, one incomplete implementation, one unrelated function and one missing-key service control. Cases 01–06 derive from case 07. Case 10 reuses exactly the case-07 source under a different credential configuration.

Ten files therefore represent nine unique source hashes, not ten independent implementations. The fixtures are intentionally correlated. They are useful for controlled demonstrations but are not a representative sample of real cryptographic projects.

For this report, each input was read, line endings normalized as the agent does, and SHA-256 recomputed. All ten hashes match their saved responses. This verifies the input/record link, not whether every provider processed the code. The combined saved inputs total 47,714 normalized UTF-8 bytes. Reported line counts include the trailing-line convention used by the application.

The saved profile hash is shared across this run. The records do not include a full application commit ID, prompt hash or schema hash, so complete historical reproducibility is not established by the source and profile hashes alone.

4. What actually produced the outputs

For cases 01–09, the saved message is:

OpenAI reported a rate or quota limit. Check the API project billing and limits.

This sentence is generated by the application's error handler. Inspection of failureMessage maps that exact text to upstream HTTP 429. The saved record does not retain the raw upstream status, error code/body or request ID on this path, so the 429 attribution comes from the implementation mapping. The data cannot distinguish exhausted quota, unavailable billing balance or a transient rate limit. It also cannot reveal internal model reasoning, because no completed model review was accepted.

Case 10 instead records:

Connect an OpenAI API key to enable GPT-6 Astra · Medium.

That is another local message. The reviewer stops at the missing-key check without submitting a model request. In both situations, deriveAssessment selects review unavailable before it considers source classification.

The sourceSent:true flag on cases 01–09 is set immediately before the outbound request. It indicates an attempted transmission path, not evidence that the provider completed inference. Tokens, cost, resolved model identity and successful response IDs are absent. Neither a zero-cost claim nor a billed-token estimate is supported.

Case 01 — Authentication failure ignored

Case 02 — Nonce reuse under one session key

Files: full source · recorded response.
Size: 130 reported lines; 5,904 bytes. Relevant requirements: F04; consequences for F02.
Intended outcome: potential_issues. Observed outcome: review_unavailable; model state error.

Code and analyst interpretation. The encryption function resets sequence to zero immediately before incrementing it. The encoded number is therefore one on every call, while the key remains the same within the object. The one-million-operation check also loses its intended cumulative effect. A successful two-message encryption run would exercise the repeated key/nonce pair; none was executed here. The defect is a state-lifecycle problem, not simply a buffer initialized with zeros.

Case 04 — Associated data omitted from authentication

Files: full source · recorded response.
Size: 129 reported lines; 5,790 bytes. Relevant requirements: F02; secondary F01.
Intended outcome: potential_issues. Observed outcome: review_unavailable; model state error.

Code and analyst interpretation. The public functions accept associated data but pass a null pointer and zero length to CNG in both directions. Encryption and decryption might still round-trip because both omit the same data. That happy-path result would not establish that metadata is authenticated. 6. Cross-case insights

6.1 This is an availability incident, not a model-quality experiment

Nine materially different review requests all failed through the same service path. Even the small sorting example did not receive an accepted scope classification. The common dependency is a stronger explanation of the observed uniformity than any property of those sources. Small inputs failing alongside larger ones also makes the application's 64-KiB input cap an implausible explanation: every fixture is comfortably below it.

This does not prove a permanent provider outage. It characterizes one short run, with one account/project configuration. The next diagnostic should be a single successful minimal Responses request after checking account billing/limits, not another full batch or a different model without authorization.

6.2 Text-pattern coverage is weak for semantic faults

The deterministic scanner produced zero observations on all six deliberately mutated inputs. As a fixture-coverage statistic, that is 0/6 mutation cases flagged by the pattern scanner. It is not an LLM recall score and does not establish a general scanner error rate.

The reason is visible in the rules: they match discarded/standalone decrypt calls, zero initializers near names such as nonce/iv, output-function names on lines containing sensitive identifiers, and ECB identifiers. They do not inspect unreachable failure branches, resetting a counter, authentication-tag arguments, omitted associated data, assignment to output or actual allocation/capacity relationships. The intentional mutations mostly require control-flow, data-flow or state reasoning.

6.3 The same baseline serves two distinct purposes

Cases 07 and 10 have equal source hashes. Their different model states—error versus missing_key—show that infrastructure configuration, not source content, determined which failure path ran. This is useful for failure-handling evaluation, but duplicating a baseline must not inflate the count of independent code examples.

6.4 “No issues” needs stronger evidence than empty findings

Every response has an empty findings list, including all intentionally faulty inputs. Empty findings therefore cannot be used as a safe-code label when the review did not complete. The current backend avoids that mistake by checking completion state first.

After successful reviews become available, a no-issues outcome will still be limited to a source review. It requires all five positive assessments and no textual observations, but those positive rationales are not checked against formal obligations. An independently reviewed baseline and executable tests are needed before using it as a reliable benchmark label.

6.6 The present records leave diagnosis gaps

The app returns local HTTP 200 with a structured unavailable report. This is defensible for an application-result endpoint, but any monitoring that counts HTTP 200 as “AI success” would falsely report 100% success here. Track application status and upstream status separately.

The error handler cancels the upstream body, losing the distinction between different 429 causes. It also loses request IDs on thrown error paths. Capture a sanitized error code/type, upstream status, request ID and retry guidance without logging the API key or unrestricted response content. Distinguish access confirmed from last review succeeded in the interface.

Finally, per-check evidenceType: llm_source_review is present even when assessment: not_reviewed. It describes the intended channel rather than evidence actually obtained. A future schema should represent “no evidence obtained” explicitly to prevent downstream misinterpretation.

6.7 Reproducibility and rerun behavior need attention

The runner resumes by loading existing response files and skips every case with a saved record, including failures. Simply rerunning it now will not refresh these ten results. A proper next run should use a new run directory/ID or an explicit rerun-failed option while preserving this original evidence. The runner also regenerates summary files, so an appended manual warning in results.md is not a durable substitute for structured run metadata.

Capture application version/commit, prompt hash, schema hash, requested and resolved model, sampling configuration, case version, source hash, tool versions and start/end timestamps. The present hashes verify source/profile identity but do not capture every factor affecting a future review.

8. Future scope: from review to verification

Stage A — Reliable source-review agent

Stabilize live access, complete the reviewed benchmark, strengthen failure diagnostics and version the prompts/rules. Keep model hypotheses, deterministic observations and verified evidence visibly separate. No self-updates should be learned from these outage records or from unreviewed model claims.

Stage B — Isolated Windows compilation and execution

Use a defined C++ adapter/interface so a trusted harness can construct keys, nonces, messages and associated data and observe outputs. Arbitrary pasted source may still receive review, but executable testing requires complete dependencies and a callable contract.

Run compilation and candidate execution in an isolated Windows environment with time/memory limits and no application credentials. Disable unnecessary network/clipboard sharing and map only minimal job data. Windows Sandbox supports these controls, but tool installation was deferred in this project. Microsoft configuration documentation.

Test reference vectors, nonempty and boundary messages, mutation of each authenticated field, output gating, buffer capacities and key/nonce lifecycle. A failed executable test can support a concrete counterexample. Passing a finite test suite should be reported as “passed these tests,” not universal security.

Stage C — Property-specific formal checking

Define the exact property and trusted boundary first. CBMC can check C/C++ assertions under stated bounds; loops, external functions and API behavior require suitable modeling. Start with small wrapper obligations such as buffer limits and “failure never releases output.” Keep bounds, assumptions, proof logs and counterexamples with the source hash. CBMC manual.

Windows CNG is an external cryptographic provider. A model that assumes authenticated decryption rejects invalid tags cannot independently prove CNG itself secure; it can establish wrapper behavior under that assumption. Missing or overly permissive stubs can create false reassurance. Distinguish failed properties, unsupported models, exhausted bounds/timeouts and proved bounded obligations.

ProVerif is suitable for symbolic protocol models and secrecy/authentication reasoning; it is not a drop-in compiler that proves arbitrary pasted C++ memory safety. It may be valuable later when the project includes protocol roles and message exchange. ProVerif.

Stage D — Additional profiles, generation and reviewed improvement

Add scheme/attacker combinations only with explicit requirements, supported libraries, reference tests and exclusions. Generation should target the same adapter and verification gates. Keep generated code untrusted until those gates complete.

After an independently reviewed testing phase, improvement can begin with versioned prompts, retrieval of approved findings and calibrated rules. Evaluate every proposed change on a held-out regression set and activate it deliberately. Updating model weights is a separate training project; the current agent does not learn automatically.

Hardware register erasure, compiler optimization, timing and physical leakage would require expanded attacker assumptions and evidence from compiled artifacts and platform-specific tools. They must not be inferred from the current AES-GCM source review.

9. Decision for the project

The architecture has explicit scope, structured output and an honest failure path. Its cryptographic review quality remains unmeasured. This run successfully records what happened and avoids substituting a security verdict for missing evidence, but it does not demonstrate detection of the six faults or recognition of the intended positive baseline.

The next milestone should be a reproducible, completed review run with independently checked expectations. Formal verification is a later, property-specific evidence layer; renaming an LLM opinion cannot replace it.
